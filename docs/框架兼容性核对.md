# P0 / P1 与 Vector 2.2、NeoZygisk 2.4 的兼容性核对

> 事实核对时间：2026-11-22。真机：小米 13（fuxi，Android 17 / SDK 37 / 4KB 页），
> KernelSU 3.3.1 + **NeoZygisk v2.4**（模块 id `zygisksu`）+ **Vector v2.2**。
> 凡标"待实测"的条目，不得当结论使用（L15）。

---

## 0. 结论（先看这三句）

1. **形态层面全部符合**：APK 的 `META-INF/xposed/*`、scope=`system`、入口类写法，以及模块包的
   `zygisk/arm64-v8a.so` + 三个脚本，都能被 Vector 2.2 与 NeoZygisk 2.4 正确识别。
2. **上一轮"maps 里没有 .so = 没注入"的判断是错的，撤回**：NeoZygisk 的设计目标之一就是
   *Trace Cleaning* —— 模块执行完后把注入痕迹从 `/proc/<pid>/maps` 里清干净。所以 maps 查不到
   **不能**否定注入。判据最终只剩一条：`/data/system/watchcat.*` 落盘文件（§5 已按实测重写）。
3. **真正卡住 ① 的只有一个技术原因**：shim 的 `DT_NEEDED` 带了 `libc++_shared.so`，而设备上只有
   `/system/lib64/libc++.so`，进程内装载时依赖解析失败 → 静默失败。已在 `1f99e13` 改为
   `-static-libstdc++` 并加硬门禁，产物复核 PASS。其余问题都是口径与规范项，不影响"能不能跑通"，
   只影响"结论可不可信"。

## 1. 两个依赖到底是什么

### 1.1 Vector 2.2

| 维度 | 事实 | 对我们的约束 |
|---|---|---|
| 定位 | Zygisk 模块形态的 ART hook 框架，内核 LSPlant（inline hook 用 Dobby），GPL-3.0 | 我们只**调用**它的 API，不再分发它的代码 |
| 系统范围 | Android 8.1 – 17 Beta | 小米 13（17）在支持范围内 |
| 运行前提 | 较新的 Magisk / KernelSU **且 Zygisk 可用**；README 直接把 NeoZygisk 列为安装示例 | 我们的组合是官方推荐路径 |
| API 代际 | 2.0=API 100；**2.1（2026-08-02）= 首个 API 101**；**2.2（2026-08-04）= API 102（热重载）** | 我们声明 101，运行时是 102，向下兼容 |
| 模块描述 | `META-INF/xposed/module.prop`（`minApiVersion`/`targetApiVersion` 必填，`staticScope`、`exceptionMode` 可选）+ `java_init.list` + `scope.list`；**模块名取 `android:label`，描述取 `android:description`** | 见 §3.1 |
| system_server 作用域 | 用**虚拟包名 `system`**；`android` 仍可作 scope（它有 `:ui` 进程不在 system_server），但勾 `android` 常常"显示启用、静默不生效" | 我们的 `scope.list` 只有 `system`，正确 |
| API 101 行为变更 | **模块不再注入 zygote，只在 scope 进程内加载** | 我们只在 system_server 里动作，契合 |
| 2.1 事故 | R8 把 `XResources` 合并进共享类，导致 system_server 内一次 `findClass` 失败即整轮开机永久失败；2.2 修复 | 与我们 L7（hook 侧不依赖资源、不开混淆）同源 |
| 已知坑 | 2.2 的 `ExceptionMode.DEFAULT` 被硬编码为 protective，`module.prop` 里的 `exceptionMode` **实际不被读取** | 声明保留即可，不要指望它切换行为 |

### 1.2 NeoZygisk 2.4

| 维度 | 事实 | 对我们的影响 |
|---|---|---|
| 定位 | 用 **ptrace** 注入 zygote 的 Zygisk 实现，给 APatch / KernelSU 补 Zygisk API，也可替代 Magisk 内置 Zygisk | 小米 13 上由它负责装我们的 `zygisk/arm64-v8a.so` |
| API 兼容性 | README 第一条原则：**与 Magisk 内置 Zygisk 的 API 完全兼容**，injector 源码按 Magisk 实现在 `loader/src/injector` 镜像 | 我们用的是 Magisk 官方 `zygisk.hpp`（`ZYGISK_API_VERSION 5`），方向正确 |
| Trace Cleaning | **模块执行完把注入痕迹从目标进程 `/proc/[pid]/maps` 彻底清除**（unmap、清 memfd） | **maps 判据作废**，改用日志 |
| DenyList 策略 | ① 直接 unmount（实验性；若某模块提供 `/product` 之类关键资源则自动放弃）② 退化为 `setns` 切到干净 mount namespace | KSU 里对应每应用的 "Umount modules"（**默认开启**） |
| Magisk 用户注意 | 应关闭 Magisk 的 "Enforce DenyList"，它和 NeoZygisk 的隔离机制会打架 | 小米 9（Magisk 31.1）上要按这条检查 |
| 极简取向 | 不做功能堆叠，日志量小 | 排障时不能指望守护进程给你长日志，得靠自己打 |

**由这两节得到的工程结论：**

- 判"注入成没成"，**只看 `/data/system/watchcat.*` 落盘文件**（含 pid / 框架版本 / 时间戳）。
  logcat 在 system_server 里抓不到、`/proc/<pid>/maps` 会被 NeoZygisk 清掉、`/data/adb/watchcat` 是
  `0700 root:root` 过不了 DAC —— 这三条都不能当判据（L15.1）。
- 我们和框架之间只有两条契约：模块包结构（`zygisk/<abi>.so`）与描述文件（`META-INF/xposed/*`）。
  这两条一旦对了，剩下全是运行期环境（DenyList、API 版本、依赖库）的问题。

## 2. 加载链路：出错时该看哪一段

```
/data/adb/modules/<id>/zygisk/arm64-v8a.so
        │  ① 守护进程 dlopen（此时只验 entry 与 api_version）
        ▼
   注入 zygote64（ptrace）
        │  ② 模块 .so 映射进 zygote
        ▼
   fork 出子进程（system_server / 普通应用）
        │  ③ 查 DenyList / umount → 决定这个进程装不装
        ▼
   preAppSpecialize / postAppSpecialize
   preServerSpecialize / postServerSpecialize   ← 我们的探针在这里打日志
        │  ④ 所有 post* 结束后，Zygisk 自卸；NeoZygisk 再清 maps 痕迹
        ▼
```

| 环节 | 失败表现 | 判定手段 |
|---|---|---|
| ① dlopen | 守护日志有 "loaded module"，但进程里零日志 | 查 `DT_NEEDED` 是否全是系统库（我们踩过 `libc++_shared.so`） |
| ② 注入 | 守护无 "injected" 行 | 看守护日志；NeoZygisk 日志量小，重点看 logcat 里 Zygisk 相关 tag |
| ③ 进程级装载 | 目标进程里完全没有模块痕迹 | 查 KSU 的 "Umount modules" / Magisk denylist 是否命中 system_server |
| ④ 回调 | 进程里有 .so 但回调没跑 | 极少见；一般是 api_version 不匹配，守护会拒绝注册 |

## 5. 判据修正（2026-11-22 实测后重写）

**三条作废的判据（都在这台机器上实测过，全部会给出假阴性）**

```bash
grep -i watchcat /proc/<pid>/maps          # ← NeoZygisk 的 Trace Cleaning 会清掉，查不到是正常的
adb logcat -b all -d | grep WatchCat       # ← system_server 里的 android.util.Log 进不了 logcat
adb shell cat /data/adb/watchcat/p0.probe  # ← 0700 root:root，system_server（uid 1000）过不了 DAC
```

**唯一判据：`/data/system` 落盘文件**

```bash
adb shell su -c 'cat /data/system/watchcat.p0.probe'
adb shell su -c 'cat /data/system/watchcat.p1_module_loaded.marker'
adb shell su -c 'cat /data/system/watchcat.p1_system_server.marker'
```

合格线：每个文件里都必须有 **pid + 时间戳 + 框架版本**，缺一项就不算证据（L15.1）。

**辅助线索（能帮助定位，但**不参与**"注入成功/失败"的判定）**

```bash
adb shell su -c 'cat /data/adb/watchcat/boot.marker /data/adb/watchcat/service.marker'   # 脚本跑过
adb shell su -c 'ls -t /data/adb/lspd/log/ | head -3'                                    # 框架加载过
```

失败时的三分支定位：

| 现象 | 大概率原因 | 下一步 |
|---|---|---|
| 守护日志有 `loaded module`，三个 `/data/system` 文件都没生成 | 依赖库缺失 / DenyList 命中 / api_version 不匹配 | 先验 `DT_NEEDED`（只许系统库），再查 KSU "Umount modules" |
| 模块脚本痕迹都没有 | 模块没装上或未合并 | 看 `/data/adb/modules/watchcat` 与 `modules_update` |
| p0 有、p1 没有 | Vector 侧没启用 / scope 不对 / 模块没装 | 看 Vector 管理器里 scope 是否只有 `system` |
| 三个文件都在但 pid 对不上 `ps -A` 里的 system_server | 读到的是上一轮开机的旧文件 | 比对文件 mtime 与本机 uptime，别把旧证据当新证据 |

## 6.1 结项：① 与 P1 都已验收（2026-11-22）

一次干净开机后（小米 13 / Android 17 / SDK 37 / KernelSU 3.3.1 + NeoZygisk 2.4 + Vector 2.2），
`system_server`（pid 1996）里拿到两组成对证据：

```
# P1：libxposed 生命周期
/data/system/watchcat.p1_module_loaded.marker
  stage=p1_module_loaded process=system system=true
  framework=Vector frameworkVersion=2.2 frameworkVersionCode=3119 api=102
/data/system/watchcat.p1_system_server.marker
  stage=p1_system_server classLoader=dalvik.system.PathClassLoader[...services.jar...]

# P0：Zig 引擎在 system_server 里可调用
/data/system/watchcat.p0.probe
  stage=postServerSpecialize pid=1996 ping=0x5743 version=0x00020000
```

三条结论：

1. **框架侧完全正常**。`onModuleLoaded` 与 `onSystemServerStarting` 都执行了，两者时间戳只差 2ms；
   Vector 2.2 对 API 101 modern 模块在 system_server 的分发没有缺陷。此前「回调未被调用」的判断撤回。
2. **判据必须改**。这台机器上 `logcat -b all` 抓不到 system_server 里的 `android.util.Log`，
   Vector 的 `log()` 又只写自己的 `/data/adb/lspd/log`；同时 `/data/adb/watchcat` 是 `0700 root:root`，
   system_server（uid 1000）DAC 直接拒绝。三条通道全黑才会被误读成「没跑」。正确判据只有一个：
   `/data/system/watchcat.*` 落盘文件。
3. **① 的 `ping` 对上了**。`ping=0x5743`、`version=0x00020000` 与 `engine.zig` 的约定一致，
   说明静态链进 shim 的是本仓库的 Zig 引擎，不是别的实现。

遗留（不影响上述结论）：

- `post-fs-data.sh` 每开机删 `armed` 是 L10 的正确行为，但旧代码「`armed` 才写 probe」会让 ① 永远无证据；
  已改成探针无条件落盘（`68ec8d0`）。
